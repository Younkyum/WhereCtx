# WhereCtx — Phase 4 (MCP Server + Webhook Dispatcher) Review

**Reviewer:** Independent staff-engineer + security/privacy critic
**Scope:** `mcp/server.ts`, `mcp/http.ts`, `webhooks/dispatcher.ts`, `index.ts`, `store/eventsStore.ts` (`listSince`), `store/webhooksStore.ts` (cursor), `store/remindersStore.ts`, `db/schema.ts` (`webhooks.cursor`), `drizzle/0001_daffy_marvex.sql`, `mcp/mcp.test.ts`, `webhooks/dispatcher.test.ts`. Cross-referenced `privacy/policy.ts`, `presence/service.ts`, `api/webhooks.ts`, `app/context.ts`, `app/server.ts`.
**Verified state accepted as given:** typecheck clean; 105/105 vitest pass; live e2e smoke (MCP over HTTP lists 7 tools, coarse view has no coords, `is_near_place` booleans, `get_precise` at home → isError; 2 webhook deliveries with valid HMAC).

---

## Summary

Phase 4 is a competent, well-shaped integration phase. The MCP tools genuinely re-apply the privacy ladder the REST surface enforces (hidden mode withholds, precise is gated through the *same* `authorizePrecise`, coarse tools never carry coords/geohash, the agent place list is name+type only), the raw-Node `/mcp` handler authenticates with strict `Bearer`-only parsing and a `read_presence` scope gate, the stateless transport cleans up on `res 'close'`, and the dispatcher is correctly store-backed (closing Phase 3's P15 — events now survive a sink outage and a restart because delivery replays from the events table via a persisted cursor). HMAC signing is correct, the timeout/abort is correct, the tick concurrency guard is sound, and the dispatcher/sweep are wired into a clean shutdown.

But this phase exposes the same handlers to a *new, unauthenticated-by-proxy-logs* surface and adds a **server-side outbound HTTP primitive**, and two real holes ship with it:

1. **SSRF.** `api/webhooks.ts` validates only that the URL is `http(s)://`. The dispatcher then does a server-side `POST` to that arbitrary URL with no block on `169.254.169.254` (cloud metadata), `localhost`/`127.0.0.1`, RFC1918, IPv6 ULA/link-local, or `*.internal`. On a self-host this is a pivot from an admin token into the host's internal network and the cloud metadata endpoint. It is admin-gated, but admin tokens are the most valuable to phish/leak and the docs position WhereCtx behind a proxy on `0.0.0.0`.
2. **Webhook event loss at same-millisecond cursor boundaries.** `listSince` uses `gt(createdAt, cursor)` (strictly-after) with the tiebreak only in `ORDER BY`, not in the `WHERE`. A single `processReading` emits `updated` + `entered_place` (+ sometimes `left_place`/`privacy_changed`) with **identical ms `createdAt`**. If a batch boundary or a delivery failure lands mid-cluster and the cursor is advanced to that ms, every *other* same-ms event is silently skipped forever. This is a correctness defect in the core delivery loop, not a theoretical one — enter/leave clusters are exactly when same-ms events occur.

Plus the deferred Phase 3 items are only **half** closed: P15 (store-backed replay) is genuinely achieved and is the strongest part of the phase, but **P16 (rate limiting), P12 (logger redaction), and P14 (read-triggered stale write) remain open**, and P16 now matters more because `/mcp` is an unthrottled, body-buffering, server-instantiating endpoint reachable by any agent token.

No CRITICAL (everything is auth-gated). Two HIGH (SSRF; same-ms cursor loss). The rest are MEDIUM/LOW.

## Findings

### WEBHOOK DISPATCHER — SSRF & delivery correctness

**H1 — HIGH — `api/webhooks.ts:26-35` + `webhooks/dispatcher.ts:149` — SSRF: operator-supplied webhook URL is POSTed server-side with no internal-address blocklist.**
`WebhookSchema` accepts any `http(s)://` URL. `WebhookDispatcher.deliver` then calls `this.fetchFn(hook.url, { method: "POST", ... })` against it. There is no guard against:
- `http://169.254.169.254/latest/meta-data/...` (AWS/GCP/Azure metadata → IAM creds on a cloud self-host),
- `http://localhost:<port>` / `http://127.0.0.1` / `[::1]` (the WhereCtx admin API itself, or any co-located service — the dispatcher becomes a confused deputy that can POST to WhereCtx's own `/v1/tokens` etc. from a trusted-localhost vantage),
- RFC1918 (`10/8`, `192.168/16`, `172.16/12`), IPv6 ULA `fc00::/7`, link-local `fe80::/10`,
- `*.internal` / `*.local` / raw cloud-internal DNS,
- DNS-rebinding (a public hostname that resolves to a private IP at fetch time).
The signed body is attacker-influenced (event payload), but the *request itself* — reaching an internal endpoint with WhereCtx's network identity — is the SSRF. It is `manage_privacy`-gated, but an admin token is the highest-value credential and the whole product is positioned for internet-exposed self-hosting; an SSRF that reads cloud metadata is a full host compromise.
**Fix:** Validate webhook URLs at create time *and* re-validate the resolved IP at delivery time (TOCTOU/rebinding). Reject hostnames that resolve to loopback, link-local, RFC1918/ULA, `169.254.0.0/16`/`fd00::`, and `0.0.0.0`. Provide a `WEBHOOK_ALLOW_PRIVATE_TARGETS` escape hatch (default off) for users who deliberately point at a LAN Home Assistant, and document it. At minimum block the metadata IP and loopback unconditionally. Resolve the host, check the A/AAAA records against the blocklist, and pin/connect to the validated IP.

**H2 — HIGH — `store/eventsStore.ts:74-81` + `webhooks/dispatcher.ts:107-117` — same-millisecond events are dropped: `gt(createdAt, cursor)` excludes sibling events that share the cursor's ms.**
`listSince` filters `gt(presenceEvents.createdAt, cursor)`. The `id` tiebreak appears in `ORDER BY` but **not** in the `WHERE`. The cursor stored by `setCursor` is `ev.createdAt` (an ISO ms string) — there is no id component. So once the cursor is advanced to `T`, *all* events with `createdAt === T` are excluded on the next read, not just the one delivered. This is reachable in normal operation:
- `emitTransitionEvents` appends `presence.updated` + `presence.entered_place` in the same synchronous `processReadingLocked` call; with a fixed/low-resolution clock (and the dispatcher's own test uses a fixed clock) they share `createdAt` to the ms. Real wall-clock `Date.now()` usually differs by 0–1ms, so this is intermittent in production and **guaranteed** under the injected-clock test harness.
- Trigger sequence: batch ends exactly between two same-ms events, OR a delivery of event A (createdAt T) succeeds and advances the cursor to T while sibling B (also T) is later in the list but the loop `break`s/continues past — on the *next* tick, `gt(.., T)` never returns B. B is lost permanently.
The existing tests don't catch it because `delivers events…` advances `nowMs += 1000` between the hook and the events but the **two events are appended back-to-back with the same `nowMs`** — they happen to both deliver in one pass *before* the cursor is persisted between them, so the in-batch loop masks the boundary case. The loss only manifests when the cursor is persisted at a same-ms event and a later tick re-queries.
**Fix:** Make the cursor a composite `(createdAt, id)` and change `listSince` to a proper keyset predicate: `createdAt > cursorTs OR (createdAt = cursorTs AND id > cursorId)`. Store both components in `webhooks.cursor` (or add a `cursor_id` column). This is the standard fix for keyset pagination over a non-unique sort key and eliminates the loss without changing the at-least-once contract.

**H3 — MEDIUM — `webhooks/dispatcher.ts:120-129` — the `maxAttempts` head-of-line guard advances the cursor past an *undelivered* event: silent, unaudited data loss with no dead-letter.**
When an endpoint fails `maxAttempts` times, the code logs `console.warn` and `setCursor(hook.id, ev.createdAt)` — i.e. it marks the event delivered and moves on. This is a deliberate HOL-unblock (documented), and unblocking is correct, but the *consequences* are not acceptable as-shipped: (a) the dropped event is gone with only a stdout warning — no dead-letter table, no `failed`/`last_error` on the webhook, no admin-visible signal, so an operator whose endpoint had a transient 30-minute outage silently loses every event in that window; (b) the in-memory `attempts` Map (see L1) means a restart resets the counter, so the actual number of attempts before drop is unbounded-or-truncated depending on restart timing; (c) `maxAttempts` defaults to 5 and the tick interval is 15s with `nudge` coalescing, so the real retry window before permanent drop can be as short as a few seconds of rapid nudges. For a presence layer that drives home-automation and reminders, dropping `entered_place` is a user-visible failure.
**Fix:** Keep the HOL unblock, but make the drop durable and visible: persist failed deliveries to a dead-letter table (or set `webhook.lastError`/`failureCount` and optionally auto-disable the hook after N consecutive permanent failures). Base the attempt count on wall-clock age, not in-memory count, so restarts don't reset it. Document the at-most-N-attempts-then-drop contract explicitly in the API.

**M1 — MEDIUM — `webhooks/dispatcher.ts:106-110` — a hook subscribed to a *subset* of event types advances its cursor past unsubscribed events, which is fine, but combined with H2 a subscribed event sharing a ms with an unsubscribed one is skipped.**
`drainHook` calls `setCursor(hook.id, ev.createdAt)` for *unsubscribed* events too (correct — it must move past them). But because the cursor is ms-only (H2), advancing past an unsubscribed `presence.updated` at ms `T` will, on the next query, also exclude a *subscribed* `entered_place` at the same ms `T`. So a hook subscribed only to `entered_place` can miss the very enter event it cares about whenever an `updated` event shares its millisecond — which is *always*, because they're emitted together. This makes H2 strictly worse for filtered hooks and is likely the most common real-world configuration.
**Fix:** Resolved by the composite cursor in H2. Worth an explicit test: hook subscribed to `entered_place` only, with `updated`+`entered_place` at the same ms, must still deliver the enter.

**L1 — LOW — `webhooks/dispatcher.ts:54` — the in-memory `attempts` Map is unbounded and not pruned on hook deletion.**
`attempts` keys are `${hook.id}:${ev.id}`. Entries are deleted on success or on max-attempts drop, but: (a) if a hook is *deleted* mid-retry, its in-flight keys leak (the hook never returns from `listActive`, so its keys are never revisited to be deleted); (b) the `pending`/`break` path leaves keys for events that are never reached again if the hook is later deleted. For a long-running server with churny webhooks this is a slow leak. Bounded in practice (few hooks, few events), but unbounded in principle.
**Fix:** Prune `attempts` keys whose `hook.id` is no longer in `listActive`, or move the counter into the DB (which also fixes H3's restart-reset). Low because the practical magnitude is small.

**L2 — LOW — `webhooks/dispatcher.ts:135-161` (`deliver`) — no response-body size cap and no redirect policy on the outbound fetch; a malicious/compromised webhook target can stream an unbounded body or 3xx-redirect to an internal address (SSRF amplifier).**
`res.ok` is read but the body is never consumed/aborted, and `fetch` follows redirects by default. A target returning a 302 to `http://169.254.169.254/...` would bypass a create-time URL check (reinforces H1's "validate at delivery / pin IP"). An endpoint returning a huge body costs memory until GC. **Fix:** Set `redirect: "manual"` (treat 3xx as failure, or re-validate the Location), and don't read the body. Tie to H1.

### MCP SERVER — auth, privacy, scope

**M2 — MEDIUM — `mcp/server.ts:169-183` — `create_location_reminder` is a WRITE exposed to `read_presence` (agent) tokens, with no hidden-mode gate, no place-existence check, no per-place/global cap, and an arbitrary place name.**
Every other MCP tool is read-only; this one calls `ctx.remindersStore.create(place, message)` and persists a row. Issues:
- **Scope mismatch.** A `read_presence` agent token can write reminders. The plan's token model (§10.4) grants agents `read_presence` (+ optional `read_precise_location`); reminder *creation* is closer to a write/automation capability. The REST surface has no reminder endpoint, so MCP is the *only* write an agent token can do — and it's unbounded.
- **No hidden-mode gate.** Unlike `is_near_place`/`get_location_age`/`list_recent_presence_events`, `create_location_reminder` does **not** call `presenceVisible()`. In `hidden` mode an agent can still create reminders (probing place names, since the place need not exist).
- **No place validation.** `place` is any 1–64 char string; it is not checked against `placesStore`. A reminder for `"nonexistent"` is stored and never fires (and `fireReminders` matches by name string, so a reminder for a place that *later* gets created with that name will fire — a latent surprise). It also lets an agent enumerate/guess place names with no feedback.
- **No cap.** No limit on reminders per place or total. An agent (or a prompt-injected one) can create unbounded reminder rows — a storage-exhaustion / DoS vector through a read-scoped token. `remindersStore.create` has no dedup and no ceiling.
**Fix:** Decide the intended scope: either require a dedicated `manage_reminders`/write scope (cleanest — agents that should create reminders get it explicitly), or keep it on `read_presence` but (a) gate on `presenceVisible()` like the sibling tools, (b) reject unknown place names with a clear error (validate against `placesStore.get(userId, place)`), and (c) cap active reminders (per place and total) returning an error past the cap. At minimum add the cap and the place-existence check to close the abuse vector.

**M3 — MEDIUM — `mcp/http.ts` + `index.ts:60-67` — the raw `/mcp` handler bypasses Hono's `bodyLimit` and the global middleware stack; it has its own 256 KB cap (4× the REST 64 KB cap) and no rate limiting, while instantiating a fresh `McpServer` + transport per request.**
Routing in `index.ts` sends `/mcp*` to the raw handler *before* Hono, so none of Hono's middleware (the 64 KB `bodyLimit`, any future CORS/rate-limit/logging) applies. Consequences:
- **Inconsistent body cap.** REST is 64 KB (Phase 3 P8 fix); `/mcp` is 256 KB. An agent token can POST 4× more to `/mcp` than to any REST route. Not catastrophic (it's capped and streamed with early `req.destroy()`), but it's an undocumented inconsistency and the larger cap is on the path that does the most per-request work (builds a server, registers 7 tools, connects a transport).
- **No rate limit (P16 still open).** Every `/mcp` POST with a valid `read_presence` token triggers a full `buildMcpServer` (7 `registerTool` calls) + `transport` + `server.connect`. There is no per-token throttle, so a leaked agent token can spin server construction in a tight loop. This is the Phase 3 P16 gap, now on a heavier code path.
**Fix:** Align the `/mcp` body cap with REST (or document why MCP needs more). Add a per-token rate limit on `/mcp` (and ingest) — the Phase 3 P16 deferral. Consider routing `/mcp` through a thin shared middleware (auth, rate-limit, body-cap) even though the transport itself must own the raw res.

**M4 — MEDIUM — `index.ts:62` — `/mcp` path matching is loose: `url.startsWith("/mcp/")` and `startsWith("/mcp?")` plus exact `/mcp` are handled, but `/mcp` is matched on the *raw* `req.url` with no normalization, and any path the three predicates miss silently falls through to Hono.**
The predicate is `url === "/mcp" || url.startsWith("/mcp/") || url.startsWith("/mcp?")`. Observations:
- `/mcp#frag` can't occur (fragments aren't sent), and `//mcp` or `/mcp%2f` would *not* match and would fall through to Hono → 404. That's fail-safe (no auth bypass, Hono just 404s), so not a vuln — but a client hitting `/mcp/` expecting the endpoint and a proxy that rewrites `//mcp` get inconsistent behavior.
- More importantly, the inverse is safe: nothing that *should* hit Hono can be tricked into the MCP handler in a way that bypasses auth, because the MCP handler authenticates independently. So this is a robustness/clarity issue, not a security one.
- There is **no `405`/method handling** distinct from POST: `GET`/`DELETE`/`OPTIONS` to `/mcp` skip `readJsonBody` (body only read for POST) and go straight to `transport.handleRequest(req, res, undefined)`. The SDK's StreamableHTTP transport returns 405 for unsupported methods *in stateless mode* and 400 for GET-without-session, so this is delegated correctly — but it's untested (no GET/DELETE test) and undocumented.
**Fix:** Parse `req.url` with `new URL(req.url, base)` and match on `pathname === "/mcp"` for clarity and to avoid the query/encoding edge cases. Add explicit tests for `GET /mcp` and `DELETE /mcp` asserting the transport's 4xx so a future SDK upgrade can't silently change behavior.

**L3 — LOW — `mcp/server.ts:104-118` (`is_near_place`) — works in `coarse` mode and reveals place proximity/identity that the coarse view deliberately withholds; it also ignores home protection (returns `inside:true` at a protected home).**
The coarse presence view (`agentCoarseView`) is carefully designed to expose status/label/motion only — no place identity. But `is_near_place("home")` returns `{inside:true, near:true}` whenever presence is visible (coarse passes `presenceVisible`), confirming the user is *at home* with a name the agent supplied. It also uses the exact stored `precise` coords internally and is not subject to `shouldHideExact` — so even when `hideHomeExactCoordinates` denies `get_precise_location`, `is_near_place("home")` still confirms "at home." This is by-design (booleans, not coords) and arguably fine — the plan explicitly lists `is_near_place` as a coarse tool — but it is a *place-identity* disclosure the coarse view avoids, and it lets an agent enumerate place names (any name → `inside/near` booleans or `no place named` error, distinguishing existing places). Consistent with Phase 3's P5/P6 unresolved "place names visible to agents in coarse mode" question.
**Fix:** Decide and document the intended exposure (consistent with the P5/P6 decision). If place names should be agent-visible, this is fine — note it. If not, gate `is_near_place` for named `home`/`work` places behind the same home-protection logic, or return a generic boolean without confirming the place exists. Low because it's booleans and a documented coarse tool.

**L4 — LOW — `mcp/server.ts:46-50` vs the read tools — `presenceVisible()` re-reads settings on every call, and `get_presence`/`get_precise_location` each independently re-fetch `settings` + `getCurrent`; a single tool call does 2–3 DB round-trips and there's no per-request caching.** Functionally correct (live settings are authoritative — good), but each MCP request builds a server and each tool call re-queries. Negligible for single-user SQLite; flag only because M3's missing rate-limit makes the per-call cost relevant. **Fix:** none required; optionally memoize settings within a single tool invocation.

**L5 — LOW — `mcp/server.ts:70` — admin `get_presence` constructs a synthetic settings object `{ ...settings, defaultAgentAccess: "coarse" }` to force a coarse view, which works but couples admin behavior to the coarse mapping; if `agentCoarseView` ever gates on another field (e.g. a future `hidden`-per-tool), the admin override silently changes.** Cosmetic/maintainability. **Fix:** Consider an explicit `buildCoarseView(presence, clock)` call for admin (it already exists and bypasses the access gate) rather than spoofing settings.

### MCP TRANSPORT — lifecycle & errors

The transport handling is mostly correct and worth crediting: stateless `sessionIdGenerator: undefined`, `enableJsonResponse: true`, `res.on("close", …)` closes both transport and server (no leak), body is streamed with an early `req.destroy()` over the cap, JSON parse errors → 400, oversize → 413, and the `catch` guards `res.headersSent` before sending 500. Two small notes:

**L6 — LOW — `mcp/http.ts:81-84` — `res.on("close", …)` closes the server/transport, but if `server.connect`/`handleRequest` throws *before* the response starts, both the `catch` (sends 500) and the `close` handler fire `transport.close()`/`server.close()`; double-close is likely idempotent in the SDK but is untested.** Also, a client that disconnects mid-stream triggers `close` → `transport.close()` while `handleRequest` may still be awaiting — relying on the SDK to tolerate that. **Fix:** none if the SDK is idempotent (it is, in current versions); add a guard flag if you want to be defensive, and note the assumption.

**L7 — LOW — `mcp/http.ts:30-53` (`readJsonBody`) — on `req.destroy()` after exceeding the cap, the promise rejects with "payload too large" *and* the `'error'`/`'close'` events may also fire; the reject is latched (Promise resolves once) so this is safe, but an empty body on a POST resolves to `undefined`, which `transport.handleRequest(req,res,undefined)` then handles — untested for the empty-POST case.** **Fix:** add an empty-body POST test; minor.

### CORRECTNESS — wiring, sweep, shutdown

**M5 — MEDIUM — `app/context.ts:41` vs `index.ts:45` — `onEvents` is typed `(events: PresenceEvent[]) => …` but wired as `() => dispatcher.nudge()`, discarding the events argument.** This is *intentional and correct* given the store-backed dispatcher (nudge re-reads from the DB cursor, so the in-memory hand-off is redundant — exactly the P15 fix). But the type now lies about the contract, and a future maintainer who wires a second `onEvents` consumer expecting the events array will be surprised that ingest/privacy/presence pass `[event]`/`result.events` that the dispatcher ignores. There is also a subtle ordering guarantee being relied on: events are persisted *before* `onEvents` is called (so `nudge` will see them) — true for ingest (`processReading` appends, then `ingest.ts` calls `onEvents`) and stale (`checkStale` appends, returns event, then presence route nudges). Verified correct. **Fix:** Either change the `onEvents` type to `() => void` to match reality, or have the dispatcher honor the passed events as an optimization. Low-to-medium because it's a latent contract mismatch, not a current bug.

**L8 — LOW — `index.ts:49-54` — the stale sweep runs `ctx.service.checkStale()` every 60s but `create_location_reminder` and other MCP writes don't nudge; reminders don't produce events so that's correct, but note the sweep only fires `became_stale` for the single configured `userId` (single-user v0.1, fine).** Also the sweep's `.then` is unguarded for rejection (`checkStale` could throw on a DB error → unhandled rejection). **Fix:** add `.catch` to the sweep's promise chain to avoid an unhandled rejection crashing the process under a transient DB error.

**L9 — LOW — `index.ts:83-88` — shutdown calls `server.close(cb)` then `closeAppContext` in the callback, with a 10s force-exit; but the `dispatcher.stop()` only clears the interval — an *in-flight* `tick()` (a webhook POST awaiting a 5s timeout) is not awaited, so the DB can be closed under it.** The dispatcher's fetch is to an external URL (not the DB), and `tick` only touches the DB via stores between awaits, so the window is small, but a tick that's mid-`setCursor` when `closeAppContext` fires could error. The `unref`'d timers and `server.close` drain HTTP, not the dispatcher. **Fix:** Track the in-flight `tick` promise and await it (with a timeout) in shutdown before `closeAppContext`, or guard store calls during shutdown. Low because the libsql client close is synchronous and the race window is narrow.

### DEFERRED FROM PHASE 3 — status

- **P15 (store-backed webhook replay) — ACHIEVED.** The dispatcher reads undelivered events from `eventsStore.listSince(cursor)` and advances a persisted `webhooks.cursor`; a sink outage or restart replays from the cursor. This is the correct architecture and the strongest part of the phase. (Caveat: H2/H3 mean replay can still *lose* same-ms or max-attempts events — the replay mechanism is right, the boundary handling is buggy.)
- **P16 (rate limiting on `/mcp` and ingest) — STILL OPEN.** No rate limiting anywhere; `/mcp` is now an unthrottled, server-instantiating endpoint (M3).
- **P12 (logger redaction) — STILL OPEN.** No structured logger landed; `mcp/http.ts:91` `console.error("mcp request error:", e)`, `dispatcher.ts:96/125` `console.error/warn`, and `index.ts` logs are raw `console.*`. The dispatcher logs hook ids and the MCP handler logs raw errors; no `authorization`/`secret`/`token` redaction. The webhook `secret` is never logged (good), but error objects from `fetch`/DB could carry URL/header fragments.
- **P14 (read-triggered stale write) — STILL OPEN (now redundant).** The periodic sweep (`index.ts:49`) now fires `became_stale`, so the `GET /v1/presence` read-triggered `checkStale` write (Phase 3 `api/presence.ts:30`) is redundant and still contends on the single SQLite writer under the per-user mutex. Phase 3's P14 anticipated dropping it once the sweep existed; it was not dropped.

### TEST ADEQUACY — concrete gaps

`mcp.test.ts` (8 tests) covers the tool list, coarse-no-coords, home-deny, booleans, places-hidden, age, hidden-withhold, and reminder-create. `dispatcher.test.ts` (4) covers happy delivery+cursor-advance, subscription filter, HMAC, and the maxAttempts skip. Untested / missing:

- **No MCP-over-HTTP test at all.** `mcp/http.ts` (auth, scope gate, body cap, routing, transport) is exercised only by the live smoke, not by an automated test. Specifically untested: **device token → 403** (the device-can-never-reach-MCP guarantee — the most important MCP auth assertion); **no token → 401**; **non-Bearer header → 401**; **`read_presence`-less token → 403**; **oversize body → 413**; **malformed JSON → 400**; **GET/DELETE/OPTIONS `/mcp`** (the SDK's 4xx, M4); **`/mcp` path routing** (`/mcp/`, `/mcp?x=1`, `//mcp` falling through to Hono).
- **No same-ms cursor test (H2/M1).** The single most impactful missing test: two events at the same `createdAt`, deliver one, advance cursor, assert the sibling is still delivered. Currently the harness's same-`nowMs` events both deliver in one pass and *mask* the bug.
- **No dedup-across-restart test.** Construct a dispatcher, deliver, persist cursor, *new* dispatcher instance (fresh `attempts` map) over the same DB, assert no re-delivery (cursor) and assert the in-memory attempt counter reset (H3/L1).
- **No SSRF test.** No assertion that `http://169.254.169.254`, `http://localhost`, RFC1918 URLs are rejected (because nothing rejects them — H1).
- **No maxAttempts data-loss assertion.** The existing test asserts the cursor *advances* (HOL unblocked) but never asserts the dropped event is recorded/dead-lettered anywhere (H3) — it implicitly accepts silent loss.
- **No redirect / response-size test** (L2).
- **No filtered-hook same-ms test** (M1) — hook subscribed to `entered_place` only, with `updated`+`enter` at the same ms.
- **No `create_location_reminder` abuse test** — unknown place name accepted, hidden-mode allows create, unbounded creation (M2).
- **No shutdown/in-flight-tick test** (L9), no stale-sweep-rejection test (L8).
- **No HMAC negative test** (wrong secret → signature mismatch) and no "no secret → no signature header" assertion.

## MUST FIX BEFORE PHASE 5

1. **(H1, HIGH)** `api/webhooks.ts` + `webhooks/dispatcher.ts` — add SSRF protection to webhook delivery. Reject (at create *and* re-validate the resolved IP at delivery) URLs whose host resolves to loopback, `169.254.0.0/16` (cloud metadata), RFC1918/ULA/link-local, or `0.0.0.0`; set `redirect: "manual"` so a 3xx can't bounce into an internal address. Provide a default-off `WEBHOOK_ALLOW_PRIVATE_TARGETS` escape hatch for deliberate LAN targets. The dispatcher is an unauthenticated-from-the-target's-view server-side POST primitive to arbitrary URLs; on a cloud self-host this reads instance credentials.
2. **(H2, HIGH)** `store/eventsStore.ts:74-81` + `store/webhooksStore.ts` cursor — fix same-millisecond event loss. Make the delivery cursor a composite `(createdAt, id)` and change `listSince` to a keyset predicate `createdAt > ts OR (createdAt = ts AND id > id)`. As shipped, advancing the cursor to a millisecond shared by multiple events (which is exactly what `updated`+`entered_place` clusters produce) silently drops the siblings — including, for a filtered hook, the very `entered_place` it subscribed to (M1).
3. **(H3, MEDIUM — blocking for a presence/automation product)** `webhooks/dispatcher.ts:120-129` — the maxAttempts HOL guard drops undelivered events with only a `console.warn`. Keep the unblock, but make the loss durable and visible: dead-letter table or `webhook.failureCount`/`lastError` + optional auto-disable, and base the attempt count on persisted/age data so a restart doesn't reset it (L1). Silent loss of `entered_place` during a transient endpoint outage is a user-visible automation failure.
4. **(Tests)** Add the MCP-over-HTTP boundary tests (device token → 403, no/again-non-Bearer → 401, missing scope → 403, 413/400, GET/DELETE `/mcp`) and the webhook tests that prove the above (same-ms delivery survives cursor advance; SSRF URLs rejected; maxAttempts drop is recorded, not silent). The current suite passes precisely because it never exercises these boundaries.

(M2 — `create_location_reminder` write-on-read-scope with no cap/place-validation/hidden-gate — is a real abuse vector and should be resolved before Phase 5, but is MEDIUM, not strictly blocking. M3's `/mcp` rate-limit/body-cap and P16/P12/P14 should be closed before any internet-exposed GA, but are the standing deferred items, not new Phase 4 blockers.)

---

## Verdict

**Conditional pass** — the MCP privacy re-enforcement is genuine and the store-backed dispatcher correctly closes Phase 3's P15, but the dispatcher ships an SSRF (no internal-address blocklist on operator URLs) and a same-millisecond cursor that silently drops co-emitted enter/leave events, and the HOL guard drops events with only a stdout warning; fix the SSRF, the composite cursor, and the dead-letter for max-attempts drops — and add the MCP-over-HTTP and same-ms boundary tests — before Phase 5.

## Resolution (applied before Phase 5)

All MUST-FIX items resolved; 125/125 tests pass (was 105), typecheck clean, live smoke re-verified.

- **H1 (HIGH) — SSRF closed.** New `webhooks/ssrf.ts` classifies private/reserved IPv4+IPv6 (loopback, `169.254/16` metadata, RFC1918, CGNAT, ULA `fc00::/7`, link-local, mapped v4). `assertSafeWebhookUrl` resolves the host and rejects private targets at **create time** (`api/webhooks.ts` → 400) **and again at delivery time** (dispatcher, DNS-rebinding defense), with `redirect: "manual"` so a 3xx can't bounce inward. Default-off `WEBHOOK_ALLOW_PRIVATE_TARGETS` escape hatch for deliberate LAN targets. Live-verified: `127.0.0.1` and `169.254.169.254` webhooks → 400 with a clear message; delivery still works when the hatch is on.
- **H2 (HIGH) — same-ms cursor loss fixed.** Delivery cursor is now composite `"<createdAt>|<id>"`; `eventsStore.listSince` uses the keyset predicate `createdAt > ts OR (createdAt = ts AND id > id)`. Tests: sibling at the same ms survives a mid-cluster cursor advance; a filtered hook's `entered_place` is delivered even when an `updated` shares its ms.
- **H3 (MEDIUM, blocking) — dead-letter instead of silent drop.** New `webhook_deliveries` table; on max-attempts the event is recorded (type + error + timestamp), the cursor advances, and `GET /v1/webhooks/dead-letters` (admin) exposes it. Test asserts the drop is recorded with the failing status.

- **L8 (LOW) — stale sweep `.catch`** added so a transient DB error can't crash via unhandled rejection.
